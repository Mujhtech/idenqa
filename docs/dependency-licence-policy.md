# Dependency Licence Policy

**Status:** Initial policy  
**Applies to:** Idenqa open-source core, its distributed binaries, public SDKs, capture packages, build tools, and generated artefacts

Idenqa is distributed under Apache License 2.0. Every new direct dependency must be reviewed before it is accepted; transitive dependencies and redistributed assets are part of that review.

## Review requirements

Record the dependency's exact version, intended use, upstream source, licence, maintenance state, relevant transitive dependencies, and known-vulnerability result in the change that introduces it. Prefer the standard library or an already accepted dependency when it meets the requirement without weakening an owned boundary.

Licence files and required attribution notices must remain present in source and binary distributions. Generated code and bundled browser or mobile assets require the same provenance review as handwritten code.

## Initial licence posture

| Category                                                                            | Initial posture                                                                                |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Apache-2.0, MIT, BSD-2-Clause, BSD-3-Clause, ISC, and similarly permissive licences | Generally acceptable after the required dependency review                                      |
| MPL-2.0, EPL, CDDL, LGPL, or other weak/file-level copyleft licences                | Requires explicit legal and distribution-impact review before selection                        |
| GPL, AGPL, SSPL, source-available, non-commercial, field-of-use, or custom licences | Not accepted into distributed core artefacts without explicit project-owner and legal approval |
| Unknown, missing, conflicting, or unverified licensing                              | Rejected until resolved                                                                        |

Build-only and test-only tools are classified separately from code linked into or redistributed with production artefacts, but their licences and provenance must still be documented and compatible with the way they are used.

This policy is an engineering intake rule, not legal advice. When classification or compatibility is uncertain, the dependency remains unselected until reviewed.
